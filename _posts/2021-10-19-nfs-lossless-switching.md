"NFS 无损切换"说的是：服务端发生故障、重启或主备切换时，客户端的业务尽量不中断，或者只中断极短时间就自动恢复。这篇文章讲这套机制靠什么实现：grace period、客户端状态恢复、租约和 delegation 的配合。核心矛盾只有一个——**状态在服务端丢了，客户端怎么重新拿回来，且不中断业务**。

## 一、无损切换要解决的核心问题

NFS 是无状态（v3）或状态化的（v4），但无论哪种，服务端一旦故障，都会面临一个问题：客户端手里握着的文件句柄、锁、delegation 还有没有效。

- NFSv3 无状态，服务端重启后 file handle 只要还在（文件系统没变），客户端重试就能继续，相对简单。
- NFSv4 有状态，服务端重启后 stateid、delegation、锁全部作废，客户端必须重新建立状态、重新拿锁。这才是无损切换真正的难点。

## 二、grace period：服务端的宽限期

服务端重启或 failover 后，会进入一个**宽限期（grace period）**。在宽限期内：

- 服务端只接受客户端的**状态回收请求**（reclaim），不接受新的锁请求。
- 目的：给客户端一个时间窗口，把之前持有的锁、状态重新要回来，防止别的客户端在这个窗口里抢走锁造成不一致。

宽限期结束，还没回收的锁就算丢了，客户端只能重新申请，这可能意味着锁的丢失（如果锁是排他的，就有冲突风险）。

## 三、客户端的状态恢复

客户端感知到服务端出问题（lease 过期、RPC 持续失败），会触发状态恢复：

1. 检测到服务端重启或切换，clientid 失效。
2. 重新 EXCHANGE_ID、CREATE_SESSION，建立新状态。
3. 把之前持有的锁、delegation 用 reclaim 重新要回来。
4. 恢复完成后，正常 IO 继续。

客户端侧这套动作由状态管理线程驱动。恢复做得快不快，直接决定切换时业务中断多久。

## 四、30 秒切换是怎么做到的

无损切换的目标是把"服务端故障 → 客户端恢复 IO"的时间压到很短，我做过目标是 30 秒内的切换。这个时间主要由几段组成：

1. 故障检测时间：客户端多久发现服务端不行了。
2. 服务端 failover 时间：主备切换、服务拉起。
3. 客户端状态恢复时间：重新建立状态、reclaim 锁。

要压时间，就得压缩每一段：故障检测要快（缩短超时）、failover 要自动化、状态恢复要精简。任何一段拖长，整体切换时间就上去了。

## 五、容易踩的坑

1. **file handle 在切换后失效**。如果 failover 到的新节点、新后端文件系统，file handle 编码或 fsid 变了，客户端手里的旧句柄全变 stale。这是切换后最常见的一类故障，我在内核升级导致的切换里就处理过 stale file handle 的问题。
2. **grace period 处理不好**。宽限期内锁没回收干净，切换后出现锁丢失或锁冲突。
3. **delegation 残留**。旧服务端授的 delegation 没清掉，客户端拿着过期 stateid 操作，得到 BAD_STATEID。
4. **切换窗口里的写丢失**。切换瞬间没落盘的写数据，如果没做好同步，会丢。

## 六、小结

无损切换的本质是**状态恢复**：服务端状态丢了，靠 grace period 给客户端一个回收窗口，客户端靠状态恢复把锁和 delegation 要回来。切换时间 = 检测时间 + failover 时间 + 恢复时间，要快就压缩每一段。而真正的坑，多在切换后状态没对齐上：stale file handle、锁丢失、delegation 残留，这些是切换之后要重点盯的。
